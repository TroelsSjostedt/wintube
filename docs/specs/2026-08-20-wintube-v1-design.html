WinTube v1

A Windows desktop port of metube — the personal YouTube client built for Apple TV. Same InnerTube recipe, same account, same viewing model; a windowed mouse-and-keyboard app instead of a 10-foot remote-driven one.

Stack WinUI 3 · .NET 8 · C# Shape Core library + app Scope Core first Repo C:\Projects\WinTube

1 · Goal and decisions already made

Build the core of the tvOS app as a native Windows desktop application, for the same single viewer. The decisions below were made during brainstorming and are settled:

InnerTube layerPorted by hand from reference/INNERTUBE.mdThe recipe is already distilled and live-verified; a third-party NuGet uses different clients and no device-flow auth.

3 · Stage 0 — playback spike (throwaway)

The one real technical risk is whether Windows plays YouTube's HLS. Before any product code is written, a minimal throwaway program answers it:

  • Call InnerTube player with the VISIONOS client and a scraped visitorData token.
  • Feed streamingData.hlsManifestUrl to MediaPlayerElement via AdaptiveMediaSource, with the client's User-Agent on media requests.
  • Verify: video and audio play, quality settles sensibly (the manifest tops out at 1080p60 H.264 for hardware decoders; VP9/AV1 variants must be ignored or handled).

If HLS fails, test the ANDROID client's muxed itag 18 (360p MP4 — plays trivially). The escape hatch is libmpv. The spike's outcome decides the player layer; nothing else in this design depends on it.

6 · Data flow

7 · InnerTube contract

Ported one-to-one from reference/INNERTUBE.md, which is live-verified. All calls are POST …/youtubei/v1/{endpoint} with a JSON context body.

ClientUsed forAuth
TVHTML5Home feed (browse "default"), search, accounts_list, FEhistoryBearer token
VISIONOSplayer → HLS multivariant manifestScraped visitorData
ANDROIDplayer → muxed itag 18 (360p) fallbackNone

Ladder behaviour (ported from StreamService.swift): a client that resolves but does not play sends the caller back with after: failedClient; LOGIN_REQUIRED/ERROR mean "try the next client" but the human-readable reason is kept and shown if the whole ladder comes up empty. An expired visitorData is retried once with a fresh token before the rejection is believed. Dubbed videos: the original audio language is read from adaptiveFormats[].audioTrack.audioIsDefault and selected explicitly, since the HLS manifest declares no default.

8 · Watch progress and history rules

Same semantics as tvOS, same numbers:

  • Position written every 5 s during playback; under 10 s counts as "opened", not watched; within 20 s of the end pins to the duration — full red line, replay starts from the beginning.
  • History = watch-progress entries (dated) folded with YouTube's FEhistory (~15 videos, undated): an undated video is placed directly below the most recent dated video, keeping YouTube's ordering, never claiming to be newer than something known newer.
  • Cards (title, channel, artwork, duration) are filled from the player's own metadata, the history list, and VideoMetadataService (VISIONOS player minus streaming), four at a time, cached for good.
  • Entries are keyed per profile and carry a dirty-set, so Appwrite sync can be added later without changing the store's shape.

9 · Error handling

  • Nothing playable → YouTube's own playabilityStatus reason, or a generic friendly line when there is none. Internal status codes are never shown.
  • Feed or search failing → an inline message with retry; the app never crashes on a network error.
  • Token refresh failing permanently → back to the login screen; stored progress stays.

10 · Testing

  • Unit tests (xUnit, on Core): feed/search/stream/auth parsing against captured real responses, scrubbed of session identifiers (visitorData, tokens) before committing — the same hygiene the metube repo applies by not committing samples at all.
  • HTTP is injected (HttpMessageHandler) so every service is testable offline.
  • Playback and UI: manual verification in v1. No UI automation yet.

11 · Stages after v1

Each is its own brainstorm-and-spec cycle, in rough order of value: Appwrite watch-progress sync (shares resume positions with the Apple TV), multiple profiles, SponsorBlock, Shorts row, channels and subscriptions, preview on hover.
