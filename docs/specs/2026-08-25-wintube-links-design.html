WinTube Links

Two user-requested features as one small stage: copy a video's YouTube URL from the player — with or without the current position — and open YouTube links in WinTube.

UI decision SplitButton (Azure DevOps-style): left half copies, chevron offers the timestamped copy Base WinTube v1 + sync + SponsorBlock

1 · Shared core — WinTube.Core.Links.YouTubeLink

MemberContract
For(videoId, at?)https://youtu.be/{id}; with a position, ?t={whole seconds}. Sub-minute positions (< 5 s) still emit the parameter when asked — the caller decides by offering the menu item or not.
TryParse(text)→ (VideoId, StartAt?) or null. Accepts absolute http(s) URLs on hosts youtu.be, youtube.com, www.youtube.com, m.youtube.com, music.youtube.com with paths /watch?v={id}, /{id} (youtu.be only), /shorts/{id}, /embed/{id}, /live/{id}; and wintube: URIs using the same watch grammar (wintube://watch?v={id}&t=90). Start time from t= or start=: raw seconds (754), with suffix (754s), or 1h2m3s form. Video ids are the 11-char [A-Za-z0-9_-] shape; anything else → null. Never treats bare text as an id (a search for an 11-letter word must stay a search).
Format(position)Position as the menu shows it: 12:34 / 1:02:34.

2 · Copy from the player

  • A SplitButton in the player's title bar, right of the title: primary half — link icon + "Copy link" — copies For(id) immediately; the chevron opens a flyout with one item, "Copy link at 12:34" (live position at open time), copying For(id, position).
  • Both confirm with the player's existing toast ("Link copied").
  • Clipboard via DataPackage + Clipboard.SetContent, as the login page already does.

3 · Opening links — three ways in

Way inBehaviour
Search boxA query that TryParses is not searched: SearchPage navigates straight to the player with the parsed id and start time.
Command lineWinTube.App.exe <url> — the first argument that parses opens the player after the shell is up (signed-in only; signed out, the app just opens normally).
wintube:// protocolRegistered idempotently at startup under HKCU\Software\Classes\wintube (URL Protocol, shell\open\command = "<exe>" "%1"). Activation parses the URI the same way.
  • Single instance: AppInstance.FindOrRegisterForKey("wintube-main") in a custom Main (DISABLE_XAML_GENERATED_MAIN); a second launch redirects its activation to the running instance and exits, and the running instance's Activated handler (marshalled to the UI thread) opens the player and fronts the window.
  • Start time wins: a parsed StartAt overrides the stored resume position for that playback — the player's navigation parameter becomes PlayerRequest(VideoItem Video, TimeSpan? StartAt); existing call sites pass StartAt: null. Progress recording is unchanged from wherever playback actually is.
  • The opened video's card starts as a placeholder (id + fallback thumbnail) when the app has never seen it; history's metadata lookup fills it in later, as History already does.

Honest limitation: clicking a youtube.com link in a browser still opens the browser — Windows has no per-site handler for desktop apps short of becoming the default browser, which this app will not do. What this stage delivers is the three ways in above.

4 · Testing

  • Unit: For with/without position; TryParse matrix — every accepted host/path shape, all three time forms, start=, wintube-grammar, and the rejections (bare 11-char text, other hosts, malformed ids, non-URLs); Format both shapes.
  • Manual (the user): both copy actions land the right URL on the clipboard; pasting a timestamped link in Search opens the player at that position; start wintube://watch?v=… from a terminal opens/reuses the running app.

5 · Out of scope

Default-browser or per-site youtube.com registration, copy from video cards (fits the future channels/context-menu stage), playlist links, and Share-charm integration.
