WinTube SponsorBlock

Automatic skipping of in-video interruptions — read-out sponsor spots, "smash that subscribe", non-music sections — using SponsorBlock's public, unauthenticated API. A port of the tvOS SponsorBlockService/SponsorBlockSkipper pair onto MediaPlayerElement.

Not ad blocking — pre/mid-rolls never reach this app; this removes the read inside the video Base WinTube v1 + sync (stage 2)

1 · Privacy model (unchanged from tvOS)

The videoId is never sent. Only the first four hex characters of its SHA-256 go to the server, which answers with every video sharing that prefix (~1/65,536 of YouTube); the match happens on device, against videoID or the full hash the server echoes. This is SponsorBlock's recommended mode and costs one slightly larger response.

2 · Core — WinTube.Core.SponsorBlock

TypeContract
SponsorCategorysponsor, selfpromo, interaction, intro, outro, preview, filler, music_offtopic — raw API identifiers on the wire, display names for the toast ("Sponsor", "Self-promotion", "Subscribe reminder", "Intro", "Outro", "Recap", "Filler", "Non-music section"). DefaultSkipped = sponsor, selfpromo, interaction, music_offtopic; the other four are editorial content and stay opt-in-less (no settings UI, as on tvOS).
SponsorSegment(Id, Category, Start, End) seconds; Contains(t) = t >= Start && t < End.
SponsorBlockServiceFetchSegmentsAsync(videoId, categories?, ct) → GET https://sponsor.ajay.app/api/skipSegments/{prefix4}?categories=[…]&actionTypes=["skip"], both params JSON arrays; categories sorted for a stable URL; User-Agent WinTube/0.1; 8 s timeout. Anything but HTTP 200 — including 404, the ordinary "no segments in this prefix" answer — and every exception → empty list. An optional enhancement must never keep a video from playing.

Filtering and merging, ported exactly: drop submissions with votes < 0 (community-disowned timestamps cut real content) and segments under 1 s (the seek costs more than the segment); sort by start and fold overlapping-or-touching segments (gap ≤ 0.5 s) into one, keeping the earlier segment's id and category — that's the one whose start the user reaches, so it's the name the toast shows.

3 · Player integration

  • Fetch after playback starts: the lookup fires on the first Playing state, so a slow third-party server can never delay the first frame.
  • Poll, don't event: a 250 ms DispatcherQueueTimer compares the position against the segment list. Polling catches every way into a segment — playing into it, a resume position landing mid-sponsor, the user scrubbing into one — where a boundary event fires only on the segment's first frame.
  • Skip once per playback: a segment's id enters a skipped-set on first contact; rewinding into it afterwards (a discount code, wrong timestamps) plays normally instead of bouncing the user forward again.
  • The seek: to min(segment.End, NaturalDuration) — a segment running to the end of the video pauses at the last frame rather than poking at end-of-stream handling.
  • Toast: "Skipped Sponsor · 42s" bottom-center for 3 s, so a chunk of video vanishing doesn't read as a stream glitch. A newer skip replaces the toast and owns its timer.
  • Cleanup: timer stopped and state cleared in OnNavigatedFrom, alongside the existing teardown; a retry/new resolve re-attaches with the same segment list.

4 · Testing

  • Unit (stubbed HTTP): URL shape (prefix-4 of a known sha256, JSON-array params, sorted categories); match by videoID and by full hash; votes<0 and <1 s dropped; overlap merge (identity kept, containment, 0.5 s touching); 404/timeout/garbage → empty.
  • Unit (selection): the "next segment to skip at time t, given the skipped-set" logic lives in Core and is tested directly.
  • Manual (the user): a video with a known sponsor read skips with a toast; rewinding into the skipped stretch plays it; playback of a segment-less video is unaffected.

5 · Out of scope

Mute-type segments, poi/chapter entries, a settings UI for categories, transport-bar segment markers (tvOS has them; add later if missed), and submitting/voting on segments.
