WinTube Sync

Watch-progress sync against the self-hosted Appwrite backend the tvOS app already uses — so resume positions travel between the Apple TV and Windows. A port of the tvOS WatchProgressSync/AppwriteClient pair; the backend itself (metube Backend/) is untouched.

Principle Local-first, best-effort, every failure silent Login None — the YouTube sign-in is the identity Base WinTube v1 (verified 2026-08-23)

1 · Identity — sharing rows with the Apple TV

The backend keys everything off tvOS's profile id, which is sha256(accountKey) truncated to 16 hex (Profile.id(for:)). WinTube stores the full 64-hex digest of the same hash, so its first 16 characters are byte-identical to the tvOS id. No migration:

ValueDerivationExample use
Sync profile idProfileId[..16] (local 64-hex truncated)Row id prefix
Appwrite user id"yt" + syncProfileId — computed by the backend, received by the appRow userId column + permissions
Row id{syncProfileId}_{videoId}Idempotent upsert; same row both devices

The metube-auth function verifies {accessToken, accountKey} by calling accounts_list itself — it needs the raw account key (obfuscated Gaia id), which v1 does not persist. StoredProfile gains an AccountKey field; a tokens.bin written before this stage backfills it with one accounts_list call and a re-save.

2 · Backend contract (from AppwriteClient.swift, verified against server 1.9.6)

CallEndpointNotes
Sign-in step 1POST /functions/metube-auth/executionsBody {"body": "<json string>", "path": "/", "method": "POST"}; the function's own status/body ride inside the execution (responseStatusCode, responseBody).
Sign-in step 2POST /account/sessions/tokenBody {userId, secret}. The session arrives ONLY as Set-Cookie: a_session_* — the body's secret is empty. Store cookie pairs; replay by hand (never a cookie container: it must survive per-profile storage).
PullGET /tablesdb/metube/tables/watchProgress/rowsqueries[] params, JSON-encoded: equal(userId), orderAsc(watchedAt), limit(100), optional greaterThan(watchedAt, since), cursorAfter(lastRowId); plus total=false.
PushPUT /tablesdb/metube/tables/watchProgress/rows/{rowId}Body {"data": {userId, videoId, position, duration, watchedAt}, "permissions": [read/update/delete for user:{userId}]}.

Headers on every call: Content-Type: application/json, X-Appwrite-Project: {projectId}, X-Appwrite-Response-Format: 1.9.5, Origin: appwrite-tvos://dk.delectosoft.metube (the tvOS platform registration is reused — zero server changes; a dedicated Windows platform can be registered later), and the stored Cookie when a session exists. Error bodies are parsed regardless of status (message is the useful part); 401 is distinguished as session-invalid → discard session, re-sign-in on the next run. Dates are ISO 8601 with fractional seconds.

3 · Sync engine rules (from WatchProgressSync.swift)

  • Local-first: the store remains the single source of truth; sync only pushes what is there and folds in what came back. Every network failure is swallowed — an unreachable home server costs nothing but the sync.
  • Push: debounced 15 s after the last local write; immediate on player close and app exit. Sequential, one row at a time; a failed row stays queued and the loop stops (next flush retries).
  • Pull: incremental by watchedAt high-water mark (persisted per profile), paged 100 rows with cursorAfter; a failed page ends the pull without advancing the mark. After the first ever successful pull, QueueAll(except: pulled) uploads the pre-sync history.
  • Merge: last-writer-wins on UpdatedAt; merged entries are never marked dirty (no echo). An unpushed local edit is newer than anything remote and survives.
  • MarkSynced guard: a pushed video's dirty flag clears only if its UpdatedAt still equals the pushed value — playback that moved on mid-upload stays queued.
  • Sign-in: single-flight; the minted session (cookie + userId) is DPAPI-persisted beside the OAuth tokens. 401 anywhere → session discarded, next run signs in afresh.
  • Triggers: app start/sign-in → pull+push; player close → immediate push; Window.Activated → sync with a 60 s cooldown (the foregrounding equivalent); app close → flush.

6 · Testing

  • Unit (stubbed HTTP): sign-in execution unwrap + cookie extraction from repeated Set-Cookie headers; query-string encoding; pull paging + high-water mark; first-pull QueueAll; LWW merge both directions; MarkSynced guard; 401 → session invalidation; debounce collapse (injectable delay).
  • Live verification (the user): watch on Windows → resume on Apple TV, and the reverse; sign out/in on Windows → history restored from the backend.

7 · Out of scope

Multiple profiles (the engine is written against one active profile, as v1 is), history-card sync (cards stay local, as on tvOS), row deletion, and any backend change.
